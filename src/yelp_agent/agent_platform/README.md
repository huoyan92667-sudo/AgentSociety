# 通用 Agent 框架

这一目录是新的通用 Agent 框架，与旧的 `agent_harness` 分开。餐饮
`recommendation_v2` 已经作为第一项真实领域能力接入，但不会控制整个 Agent；
以后旅游、酒店、景点等能力可以继续通过同一工具边界注册。

## 第一批：运行骨架

当前骨架已经能够：

1. 接收用户编号、会话编号、用户消息和当前时间；
2. 从只追加的会话事件中还原模型历史；
3. 让模型选择直接回答、询问用户或调用工具；
4. 在一轮中反复执行“模型判断 → 工具执行 → 模型继续判断”；
5. 统一注册工具并生成给模型看的参数结构；
6. 让所有工具经过执行前处理、最终检查、执行包装、执行后处理和最终观察；
7. 统一处理参数错误、未知工具、拒绝、超时、异常、输出检查和结果截断；
8. 统计主模型及工具内部模型的词元、模型次数、工具次数和整体耗时；
9. 使用统一持久化接口保存完整会话事件；
10. 使用假模型和假工具完成不访问网络的循环测试。

## 第二批：持久化

第二批已经完成：

1. PostgreSQL 异步连接和连接池；
2. Alembic 数据库升级脚本；
3. 会话、轮次和只追加事件持久化；
4. 主模型每次调用的模型、词元和耗时记录；
5. 餐饮、旅游等领域状态的完整版本快照；
6. 领域状态并发版本检查，拒绝旧状态覆盖新状态；
7. 推荐审计、完整评论等大结果的编号和摘要索引；
8. 超过阈值的大结果自动转存到独立文件，数据库保存结果编号；
9. 普通工具结果保留正式输出；正式值与给模型的正文相同时，数据库只存一份，回放时原样恢复；
10. 应用异常退出后，将未完成轮次标记为中断并允许继续对话。

详细配置和表结构见 [persistence/README.md](persistence/README.md)。

## 第三批：真实模型和餐饮工具

第三批已经接入：

1. 使用项目现有 `OPENAI_API_KEY`、`OPENAI_BASE_URL` 和 `OPENAI_MODEL`
   配置连接 DeepSeek 等 OpenAI 兼容模型；
2. 主模型能够原生返回工具调用，不再用自由文字伪造工具名称和参数；
3. 主模型负责判断直接回答、重新推荐、查已有商家事实、读取14项离线评论特征，
   还是针对长尾问题实时检索真实评论；
4. `recommend_restaurants` 直接接收运行时注入的用户原话，模型只能决定是否调用，
   不能在抄写参数时漏掉“必须、地道、晚上几点”等要求；
5. 完整推荐内部继续执行四路融合、地点距离、结构化硬过滤和评论证据排序；
   工具把正式的 Top5、满足档位及正反证据交给主模型，由主模型组织最终回答；
6. `search_restaurant_businesses` 可以把用户直接说出的店名转换为真实商家编号；
7. `lookup_business_facts` 可按商家编号读取地址、评分、价格档位、历史营业时间、
   停车等已有结构化事实；
8. `lookup_business_aspect_evidence` 读取500家餐厅14项离线特征的程度档位、
   证据充分程度、争议程度和代表性评论；
9. `search_business_review_evidence` 接收主模型已经确定的商家编号和自然语言证据问题，
   再在指定商家的评论内执行关键词与向量混合检索；
10. 主模型必须保留推荐工具给出的固定顺序，不能替换商家；但可以结合用户原话、
    每项满足档位、证据充分程度和代表性评论决定怎样解释；
11. 推荐的完整统一状态写入 PostgreSQL，进程重启后可恢复并继续修改；
12. 推荐工具不再把几百个内部候选和淘汰轨迹写入会话，只保存正式 Top5、证据和
    过滤摘要；耗时与词元走统一运行记录，不重复混入给模型的推荐正文；
13. 完整推荐内部的模型调用次数、输入输出词元和耗时会合并到整轮统计中。
14. 需求融合和评论检索说法改写已经合成一次模型调用，评论排序不再单独调用模型。
15. 原有独立推荐工作流仍支持逐片输出；接入通用 Agent 后，最终回答改由主模型生成，
    下一批需要把主模型本身也接成流式输出。

## 第四批：通用上下文和会话记忆

当前已经完成第一版通用记忆，不绑定餐厅字段：

1. 每轮调用模型时，只带最近六轮已经结束的原始问答，以及当前轮完整的工具调用链；
2. 旧轮次的工具调用、检索候选和中间过程不会在以后每一步反复回放；
3. 工具可以用真实结果更新“当前关注对象、最近有序结果、业务状态版本和待补充问题”；
4. 最近推荐列表最多保存十项，因此“第三家”会稳定对应真实商家编号，而不是让模型猜；
5. 尚未总结的旧对话达到六轮或字符上限后，模型把最老部分压成短摘要，最近四轮保留原话；
6. 摘要正文由模型生成，但来源轮次、真实对象编号、结果编号和时间由程序补充，模型不能伪造；
7. 主模型只有在用户追问更早内容时，才调用 `search_conversation_memory` 搜索旧摘要；
8. 摘要不够时，该工具可以取回对应轮次的用户原话和最终回答，但不会重新载入旧工具链；
9. 工作记忆和对话摘要都持久化到 PostgreSQL，重启后继续可用；
10. 每次上下文记录各部分字符量和包含轮数，方便直接比较压缩前后的词元变化。
11. 每个会话的轮次使用严格递增编号判断摘要边界，不再依赖可能相同的结束时间。

这套结构同样能记录旅游景点、酒店、行程或普通任务。餐饮的完整融合状态仍留在餐饮自己的
版本表里，通用记忆只保存指向最新版本的编号，不复制一份容易不一致的数据。

DeepSeek、PostgreSQL、Qdrant 和完整餐饮工具链验证：

- 工具固定返回 Barry's Steaks、Barclay Prime、Alpen Rose、Picanha Brazilian
  Steakhouse、Broncos Brazilian Steakhouse 五家，主模型完整保留顺序；
- 工具正式正文由截断前的约 2.46 万字符降为 1.77 万字符，截断警告从 1 条降为 0；
- 精简的是重复字段和非回答所需的性能明细，满足档位、证据充分程度、争议程度、
  正面证据、反面证据、基础评分、距离与停车事实仍然保留；
- 工具内部约 5.10 秒，整轮约 16.00 秒；整轮输入 13,032 词元、输出 1,845 词元；
- 最终五家全部生成完毕，没有再次在第三家附近中断；
- 后续同一结构化值与模型正文不再在事件里保存两遍，模型回放内容保持不变。

### 2026-09-02：单店追问改为主模型自由选择工具

主模型现在负责理解整句话并决定连续调用什么能力，程序不再把所有单店追问塞进一条固定流程：

```text
“第三家服务怎么样”
→ 从历史 presented_businesses 读取第三家的 business_id
→ 调用 lookup_business_aspect_evidence(service)

“第三家最近有没有服务慢的差评”
→ 从历史读取 business_id
→ 调用 search_business_review_evidence(近期服务慢)

“Alpen Rose 有停车场吗”
→ 历史没有编号时先调用 search_restaurant_businesses
→ 再调用 lookup_business_facts

“Alpen Rose 有停车场而且停车方便吗”
→ 先查结构化停车事实
→ 再查离线停车证据或实时评论证据
```

主模型只决定“查什么、查哪家、需要哪些工具”。工具负责真实编号、数据库读取、
关键词与向量混合检索、按评论编号去重和证据返回。实时评论工具不会再次判断用户
究竟想查商家属性还是评论观点，也不会要求主模型填写关键词、同义句或向量。

固定14项和长尾查询共用同一套评论资源：命中已有500家离线画像时直接读取；长尾
问题才启动本地向量模型和Qdrant。完整推荐和单店实时查询共享同一份向量资源，避免
一个进程重复加载两套本地模型。

真实应用装配入口是 [application.py](application.py)，命令行验证入口是
[real_restaurant_demo.py](real_restaurant_demo.py)。

### 运行真实餐饮对话

先保证 PostgreSQL 已升级且 Qdrant 评论集合已启动，再设置数据库地址：

```powershell
$env:AGENT_DATABASE_URL = 'postgresql+asyncpg://agent:agent_dev_password@localhost:5433/agent'
.\.venv\Scripts\python.exe -m yelp_agent.agent_platform.real_restaurant_demo `
  '我今天晚上7点想吃牛排' `
  --follow-up '第二家的停车情况怎么样？' `
  --user-id '真实用户编号' `
  --session-id '一个稳定的会话编号'
```

`--follow-up` 可以重复提供；这些问题会在同一个应用进程中依次执行。同一个会话
编号再次运行时，也会从 PostgreSQL 恢复上一轮完整餐饮状态。
服务进程首次建立餐饮工具时需要加载本地评论向量模型；正式常驻服务只在启动时
加载一次，不应为每条用户消息重新启动模型。

增加 `--stream` 后，命令行结果会记录第一段文字到达时间、收到的片段数，以及
所有片段拼接后是否与最终保存的完整答案一致。应用层也可以直接遍历
`RestaurantAgentApplication.handle_stream(...)`，持续接收 `answer_delta`，最后
接收一次 `final`。这些小片段不会作为会话事件逐条写入数据库。

### 2026-08-26 最新真实联调结果

最新测试使用真实用户 `ET8n-r7glWYqZhuR6GcdNw` 和问题“我想吃牛排”：

- 主模型主动选择 `recommend_restaurants`；
- 整轮只有一个 Agent 步骤和一个工具调用；
- 推荐内部把需求融合和评论检索说法合成一次模型调用，因此 Agent 整轮模型调用由 4 次降为 3 次；
- 输入 5,603 词元，输出 1,221 词元，合计 6,824 词元，整轮约 16.46 秒；
- 用户约 7.43 秒看到第一段回答，共收到 804 个片段，拼接结果与最终保存答案完全一致；
- 本地评论向量模型首次加载约 14.90 秒，只在应用启动时发生一次，不计入单轮 16.46 秒；
- 评论证据排序约 1.67 秒；旧实现约 8.06 秒；
- 首轮评论库查询返回 296 条命中关系，只有 1 家扩大到第二档并补回 124 条，没有商家进入第三档；
- 评论库不再返回 1,024 维向量，最终只从本地文件读取 130 个不同片段向量，耗时约 7.3 毫秒；
- 最终只加载 115 条完整评论；旧实现加载 2,034 条；
- PostgreSQL 没有保存 804 条逐片输出事件，只保存完整回答、完整状态、紧凑商家快照和 1 份压缩审计结果。

与优化前同类测试相比，总词元从 6,877 仅降到 6,824，说明本批主要解决的是评论检索耗时和首段等待，而不是彻底解决回答生成成本。新测试中最终回答生成约 9.25 秒，是当前整轮最大的耗时来源。

本次四路融合把牛排识别成 `Steakhouses` 类别硬条件，类别过滤由 2,447 家降到 62 家。由于用户没有说明到店时间，旧默认规则又按请求发生时的费城当地时间 09:27 执行“当时营业”硬过滤，最终只剩 4 家。这个结果已确认是默认营业规则过重，不是距离、长期画像或评论排序删除了商家，后续需要修改。

此前同一会话追问“第二家的停车情况怎么样”也已跑通：主模型从上轮快照定位商家，只调用 `lookup_business_facts`，不重新运行推荐；停车费用、免费与否、减免和报销保持未知，不会从其他停车字段擅自推断。

## 对外入口

应用层只需要创建 `AgentRuntime`，然后调用：

```python
result = await runtime.handle(
    AgentTurnInput(
        user_id="user-1",
        session_id="session-1",
        message="第二家服务怎么样？",
    )
)
```

调用方不需要自己管理模型循环、工具结果回填、计时和事件记录。

## 工具执行顺序

```text
记录模型产生的工具调用
→ 检查工具是否存在
→ 验证参数结构
→ 执行前处理
→ 只允许拒绝的最终检查
→ 超时、重试和执行包装
→ 真正执行工具
→ 验证工具输出
→ 执行后处理
→ 固化不可原地修改的结果
→ 最终结果观察
→ 记录工具结果
→ 把工具声明的正式输出交回模型
```

具体工具只关心输入、实际业务和输出。日志、计时、异常和结果格式由统一流水线处理。

## 会话记录

正式运行使用 `PostgresAgentPersistence`。`MemorySessionStore` 保留给快速测试，
两者遵守相同接口。事件按照每个会话独立递增的序号只追加，包括：

```text
session/created
turn/start
user/message
step/start
model/request
assistant/message
tool/call
tool/result
step/end
turn/end
```

事件仍是故障恢复和审计的完整事实来源，但模型不会每次读取所有事件。它只读取近期问答、
当前轮工具链、当前工作记忆和少量旧话题摘要。
