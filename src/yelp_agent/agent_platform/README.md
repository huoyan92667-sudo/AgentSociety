# 通用 Agent 框架

这一目录是新的通用 Agent 框架，与旧的 `agent_harness` 分开。餐饮
`recommendation_v2` 已经作为第一项真实领域能力接入，但不会控制整个 Agent；
以后旅游、酒店、景点等能力可以继续通过同一工具边界注册。

## 第一批：运行骨架

当前骨架已经能够：

1. 接收用户编号、会话编号、用户消息和当前时间；
2. 从只追加的会话事件中还原模型历史；
3. 让模型选择直接回答、询问用户或调用工具；
4. 在一轮中反复执行“模型判断 → 工具执行 → 模型继续判断”；
5. 统一注册工具并生成给模型看的参数结构；
6. 让所有工具经过执行前处理、最终检查、执行包装、执行后处理和最终观察；
7. 统一处理参数错误、未知工具、拒绝、超时、异常、输出检查和结果截断；
8. 统计主模型及工具内部模型的词元、模型次数、工具次数和整体耗时；
9. 使用统一持久化接口保存完整会话事件；
10. 使用假模型和假工具完成不访问网络的循环测试。

## 第二批：持久化

第二批已经完成：

1. PostgreSQL 异步连接和连接池；
2. Alembic 数据库升级脚本；
3. 会话、轮次和只追加事件持久化；
4. 主模型每次调用的模型、词元和耗时记录；
5. 餐饮、旅游等领域状态的完整版本快照；
6. 领域状态并发版本检查，拒绝旧状态覆盖新状态；
7. 推荐审计、完整评论等大结果的编号和摘要索引；
8. 超过阈值的大结果自动压缩到独立文件；
9. 工具结果进入会话前自动替换成结果编号，避免一万多行内容进入历史；
10. 应用异常退出后，将未完成轮次标记为中断并允许继续对话。

详细配置和表结构见 [persistence/README.md](persistence/README.md)。

## 第三批：真实模型和餐饮工具

第三批已经接入：

1. 使用项目现有 `OPENAI_API_KEY`、`OPENAI_BASE_URL` 和 `OPENAI_MODEL`
   配置连接 DeepSeek 等 OpenAI 兼容模型；
2. 主模型能够原生返回工具调用，不再用自由文字伪造工具名称和参数；
3. 主模型负责判断直接回答、重新推荐，还是查询已有商家事实；
4. `recommend_restaurants` 直接接收运行时注入的用户原话，模型只能决定是否调用，
   不能在抄写参数时漏掉“必须、地道、晚上几点”等要求；
5. 完整推荐内部继续执行四路融合、地点距离、结构化硬过滤、评论证据排序和
   最终自然总结，不能由主模型跳过或改变先后顺序；
6. `lookup_business_facts` 可按商家编号读取地址、评分、价格档位、历史营业时间、
   停车等已有结构化事实；
7. 推荐成功后直接使用证据总结作为本轮最终回答，外层主模型不能再次改写排序、
   删除风险或增加无证据结论；
8. 推荐的完整统一状态写入 PostgreSQL，进程重启后可恢复并继续修改；
9. 完整推荐审计结果过大时自动保存成独立压缩文件，会话历史只保留结果编号、
   精简 Top5 和最终回答；
10. 完整推荐内部的模型调用次数、输入输出词元和耗时会合并到整轮统计中。
11. 需求融合和评论检索说法改写已经合成一次模型调用，评论排序不再单独调用模型。
12. 最终推荐总结支持逐片返回；流式片段只发给当前调用方，PostgreSQL 仍只保存完整答案。

真实应用装配入口是 [application.py](application.py)，命令行验证入口是
[real_restaurant_demo.py](real_restaurant_demo.py)。

### 运行真实餐饮对话

先保证 PostgreSQL 已升级且 Qdrant 评论集合已启动，再设置数据库地址：

```powershell
$env:AGENT_DATABASE_URL = 'postgresql+asyncpg://agent:agent_dev_password@localhost:5433/agent'
.\.venv\Scripts\python.exe -m yelp_agent.agent_platform.real_restaurant_demo `
  '我今天晚上7点想吃牛排' `
  --follow-up '第二家的停车情况怎么样？' `
  --user-id '真实用户编号' `
  --session-id '一个稳定的会话编号'
```

`--follow-up` 可以重复提供；这些问题会在同一个应用进程中依次执行。同一个会话
编号再次运行时，也会从 PostgreSQL 恢复上一轮完整餐饮状态。
服务进程首次建立餐饮工具时需要加载本地评论向量模型；正式常驻服务只在启动时
加载一次，不应为每条用户消息重新启动模型。

增加 `--stream` 后，命令行结果会记录第一段文字到达时间、收到的片段数，以及
所有片段拼接后是否与最终保存的完整答案一致。应用层也可以直接遍历
`RestaurantAgentApplication.handle_stream(...)`，持续接收 `answer_delta`，最后
接收一次 `final`。这些小片段不会作为会话事件逐条写入数据库。

### 2026-08-26 最新真实联调结果

最新测试使用真实用户 `ET8n-r7glWYqZhuR6GcdNw` 和问题“我想吃牛排”：

- 主模型主动选择 `recommend_restaurants`；
- 整轮只有一个 Agent 步骤和一个工具调用；
- 推荐内部把需求融合和评论检索说法合成一次模型调用，因此 Agent 整轮模型调用由 4 次降为 3 次；
- 输入 5,603 词元，输出 1,221 词元，合计 6,824 词元，整轮约 16.46 秒；
- 用户约 7.43 秒看到第一段回答，共收到 804 个片段，拼接结果与最终保存答案完全一致；
- 本地评论向量模型首次加载约 14.90 秒，只在应用启动时发生一次，不计入单轮 16.46 秒；
- 评论证据排序约 1.67 秒；旧实现约 8.06 秒；
- 首轮评论库查询返回 296 条命中关系，只有 1 家扩大到第二档并补回 124 条，没有商家进入第三档；
- 评论库不再返回 1,024 维向量，最终只从本地文件读取 130 个不同片段向量，耗时约 7.3 毫秒；
- 最终只加载 115 条完整评论；旧实现加载 2,034 条；
- PostgreSQL 没有保存 804 条逐片输出事件，只保存完整回答、完整状态、紧凑商家快照和 1 份压缩审计结果。

与优化前同类测试相比，总词元从 6,877 仅降到 6,824，说明本批主要解决的是评论检索耗时和首段等待，而不是彻底解决回答生成成本。新测试中最终回答生成约 9.25 秒，是当前整轮最大的耗时来源。

本次四路融合把牛排识别成 `Steakhouses` 类别硬条件，类别过滤由 2,447 家降到 62 家。由于用户没有说明到店时间，旧默认规则又按请求发生时的费城当地时间 09:27 执行“当时营业”硬过滤，最终只剩 4 家。这个结果已确认是默认营业规则过重，不是距离、长期画像或评论排序删除了商家，后续需要修改。

此前同一会话追问“第二家的停车情况怎么样”也已跑通：主模型从上轮快照定位商家，只调用 `lookup_business_facts`，不重新运行推荐；停车费用、免费与否、减免和报销保持未知，不会从其他停车字段擅自推断。

## 对外入口

应用层只需要创建 `AgentRuntime`，然后调用：

```python
result = await runtime.handle(
    AgentTurnInput(
        user_id="user-1",
        session_id="session-1",
        message="第二家服务怎么样？",
    )
)
```

调用方不需要自己管理模型循环、工具结果回填、计时和事件记录。

## 工具执行顺序

```text
记录模型产生的工具调用
→ 检查工具是否存在
→ 验证参数结构
→ 执行前处理
→ 只允许拒绝的最终检查
→ 超时、重试和执行包装
→ 真正执行工具
→ 验证工具输出
→ 执行后处理
→ 固化不可原地修改的结果
→ 最终结果观察
→ 记录工具结果
→ 把精简内容交回模型
```

具体工具只关心输入、实际业务和输出。日志、计时、异常和结果格式由统一流水线处理。

## 会话记录

正式运行使用 `PostgresAgentPersistence`。`MemorySessionStore` 保留给快速测试，
两者遵守相同接口。事件按照每个会话独立递增的序号只追加，包括：

```text
session/created
turn/start
user/message
step/start
model/request
assistant/message
tool/call
tool/result
step/end
turn/end
```

模型历史从这些事件中重新生成，不另外保存一份可能与事实不一致的消息历史。
