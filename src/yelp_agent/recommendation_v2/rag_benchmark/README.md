# 单问题全量评论召回评测

这个目录只验证一件事：当前评论召回有没有从硬筛商家的全部评论中找回真正相关的正反证据。

它不会先用当前向量检索挑几十条候选再让模型标注。真实顺序是：

1. Claude Code 中的 GLM-5.1 根据真实可执行范围生成一个自然问题。
2. 现有四路融合模块把问题整理成统一结构；第一轮没有历史、画像和场景时，这三路允许为空。
3. 现有地点工具和硬筛工具得到全部候选商家。
4. 从原始评论表中读取这些商家的全部完整评论。
5. 评论只因模型容量分批，每条评论必须恰好标注一次。
6. 当前 Qdrant 评论召回在同一个商家范围和同一个问题上运行。
7. 用真实评论编号比较命中、漏召回、错误方向和错误证据。

如果现有融合因为“地点没有被解析成纯数字经纬度”而失败，报告会原样记录失败，评测则使用已经由题目固定的费城唐人街真实中心坐标继续运行。这个补充只用于隔离评论召回测试，不会写回推荐会话，也不会放宽统一结构。

第一次真实尝试证明200条完整评论一批过大：单批耗时约448秒，并把一个真实评论编号的最后一个字符抄错。默认值因此改为每批最多50条、最多4批并行；这只改变装箱和执行速度，不会抽样或丢弃评论。每批失败会独立重试一次。

GLM 有时会把 `ambiguous` 或 `irrelevant` 的证据程度写成 `weak`。这两类评论本来就不进入正反证据分数，程序会固定把它们的程度补成 `none`，但不会改动评论方向、编号或原文证据。

提示词在 `prompts/`，可以直接检查。代码的公开入口只有：

```python
run_single_case_benchmark(config)
```

真实运行数据写入：

```text
recommendation_v2/data/rag_benchmark/v1/cases/<case_id>/
```

其中 `inputs/` 是交给 GLM 的全部批次，`raw_outputs/` 是未经修改的模型返回，`hidden/` 是逐评论正确答案，`audit/` 是当前召回和漏召回明细。

## 查找说法和两路召回对比

`retrieval_experiment.py` 复用已经完成的全量评论标签，不再重复让模型标注。它会分别测试每边使用 1、2、3、4、5 条正反说法，并同时比较：

- 只按意思找；
- 按意思和按关键词同时找，再按两边名次合并。

每个组合默认重复三次，分别保存启动耗时、查询说法向量化耗时、两条查询路线耗时、合并耗时、召回数量和正确答案召回率。结果写入案例的 `audit/retrieval_ablation.json`。这项实验不修改评论正反方向、时间数量聚合和商家评分。
