# 新版餐饮推荐系统：当前实现、真实流程与 Agent 运行框架

> 更新时间：2026-08-26  
> 项目位置：`src/yelp_agent/recommendation_v2/`  
> 文档用途：给后续接手的开发者或大模型快速补齐上下文，避免继续按照旧 Agent 系统理解当前项目。

## 一、先说最重要的结论

当前的新推荐系统已经不再以“根据历史猜用户下一次会去哪家餐厅”为核心目标，也不再以旧系统的排序模型为中心。

现在真正要解决的问题是：

```text
把用户这一轮明确说的要求
+ 之前对话仍然有效的要求
+ 用户长期画像
+ 当前场景的一般默认倾向
融合成一份完整要求
    ↓
先用必须满足的条件过滤餐厅
    ↓
再用有先后顺序的偏好和真实评论证据排序
    ↓
最后根据商家事实、正面证据和反面证据生成推荐回答
```

这套新版系统有三个必须分清的状态：

1. **已经实现并真实跑通的部分**：统一要求、四路融合、地点距离、营业时间、硬过滤、评论证据检索、证据排序、自然语言回答、Agent 工具选择、PostgreSQL 持久化、完整运行统计和逐片返回回答。
2. **仍然保留但不属于正式在线主流程的实验代码**：旧的评论词表粗筛、旧的前十家逐条大模型判断方案、旧排序兜底等。
3. **已经发现但还没有解决的部分**：没有明确到店时间时错误地按“现在营业”严格过滤、画像偏好与本轮问题相关性不足、主营类别与附带类别未区分，以及新版完整测评体系尚未建立。

当前餐饮推荐内部仍然保持固定且可审计的顺序，但外层已经接入通用 Agent 运行框架。主模型可以判断是重新推荐、直接回答、按名称找商家、查询已有商家事实、读取固定14项离线评论证据，还是针对长尾问题实时检索评论；一旦选择完整推荐，内部仍固定执行四路融合、硬过滤、评论证据排序和最终总结，不能由主模型随意跳步。

### 2026-09-02：商家追问不再使用一条写死流程

单店追问现已拆成四种可由主模型自由组合的能力：

1. 按名称寻找真实商家编号；
2. 按编号读取地址、营业时间、评分、类别、停车场等结构化事实；
3. 按编号读取500家餐厅已经离线计算好的14项特征、证据充分程度、争议程度和代表性原评论；
4. 按编号和任意自然语言问题，在指定商家评论中实时执行关键词与向量混合检索。

大模型负责结合整句和会话历史决定调用哪个工具。例如“有停车场吗”查结构化事实，
“停车方便吗”查评论特征，“最近有没有停车难的差评”实时查具体评论；一个问题也可以
连续调用多个工具。程序只负责真实编号、查询范围、参数校验、评论去重和证据原文，
不再替主模型用关键词规则决定用户意图。

### 2026-08-26 这一批具体改了什么

本批修改围绕三个实际问题展开：评论检索太慢、模型调用重复、回答生成期间用户长时间看不到内容。下表以已经完成真实调用验证的内容为主；仅完成本地回归测试的项目会单独标明。

| 实际问题 | 修改前 | 采用的解决办法 | 修改后 | 当前结论 |
|---|---|---|---|---|
| 四路融合后又单独调用一次模型生成评论检索说法 | 整轮共调用 4 次模型；融合与检索说法分成两次 | 让同一次模型调用同时输出当前完整要求和必要的正反评论检索说法 | 整轮降为 3 次模型调用 | 已完成真实验证 |
| 评论库每次把 1,024 维向量跟结果一起传回 | 首轮产生 6,902 条命中关系，后续又整理成大量重复片段 | 评论库只返回片段编号和事实；再按编号从本地向量文件读取真正需要的不同片段 | 首轮 296 条命中关系，补查 124 条；最终只读取 130 个不同片段向量，本地读取约 7.3 毫秒 | 已完成真实验证 |
| 所有商家一开始都按大数量召回评论 | 评论库首轮查询约 3.54 秒，完整评论读取 2,034 条 | 先每家每种说法取 15 条；只有结果取满且明确证据不足 5 条时，才扩大到 30，再不足才扩大到 60 | 本次只有 1 家进入第二档，没有商家进入第三档；完整评论读取 115 条 | 已完成真实验证 |
| 用户必须等完整回答生成完才能看到结果 | 整轮约 17.63 秒后才能拿到回答 | 最终回答按生成片段立即返回，数据库只保存拼好的完整回答 | 新实测约 7.43 秒看到第一段，整轮约 16.46 秒；804 个片段拼接后与最终答案完全一致 | 已完成真实验证 |
| 返回不足 5 家时，回答模板仍假定一定有 5 家 | 只剩 4 家时可能出现“第五家不存在”的解释 | 把真实返回数量交给回答模型，并明确禁止增加、删除商家 | 实测只介绍实际存在的 4 家 | 已完成真实验证 |
| 最终回答结尾再次比较商家，削弱程序已经排好的顺序 | 真实回答结尾额外强调第 3、第 4 家 | 明确要求介绍完最后一家后直接结束，不再追加“综合来看”式二次比较 | 代码和本地回归测试已经通过 | 还需要下一次真实外部调用复核 |
| 大量运行细节被误认为都会写入下一轮上下文 | 完整审计结果可达上万行，容易误以为会话也保存全部正文 | PostgreSQL 只保存会话事件、完整状态、前几家紧凑快照和结果编号；大结果压缩到独立文件 | 本次数据库没有保存任何逐片输出记录，只保存 1 份压缩审计结果 | 已完成真实验证 |

旧记录中的“6,902 条命中关系”不是 6,902 条不同评论。一个片段可以同时命中多个偏好、同一偏好的正面说法和反面说法，因此会重复形成多条“本轮要求—评论片段”关系。旧代码报告的 4,108 也不是全局不同片段数，而是分别在每条要求内部去重后再相加，同一片段跨要求仍会重复。新实现合并全部要求后全局去重，本次真正需要读取向量的片段只有 130 个。

合并模型调用也经历过一次失败尝试。第一次让模型在线生成全部固定特征的检索说法后，融合阶段上升到约 10.74 秒，整轮约 21.28 秒，第一段回答约 15.09 秒才出现。现在只让菜品相关的食物质量、分量、辣度结合本轮问题动态生成，其余含义稳定的固定特征读取离线描述，才得到表中的最终结果。

这轮优化没有显著降低总词元。旧实测为输入 5,808、输出 1,069、合计 6,877；新实测为输入 5,603、输出 1,221、合计 6,824。输入略有下降，但新回答更长，抵消了节省量。因此，这一批最明确的收益是评论检索从约 8.06 秒降到约 1.67 秒，以及用户能更早看到回答；最终回答本身仍然是当前最大、最不稳定的耗时来源。

## 二、不要再拿旧 Agent 系统套当前项目

旧 Agent 里曾经存在自由选择工具、旧排序模型、旧商家字段和旧测评目标。它们现在最多只能作为工程参考，不能被当作新版推荐的真实执行逻辑。

新版正式入口当前不会使用旧的画像排序模型，也不会先让旧模型排一个顺序再做评论排序。新版直接在满足硬条件的全部候选餐厅中，根据当前有效偏好、评论证据、Yelp 评分和距离计算最终顺序。

新版目前复用旧项目的内容主要是：

- Yelp 原始商家和评论数据；
- 真实用户长期画像存储；
- 通用的大模型调用封装；
- 本地文字向量模型等底层能力。

新版自己的状态、商家事实、类别表、硬过滤、评论库、排序和回答，都位于 `recommendation_v2` 目录中。

## 三、当前系统的五条核心原则

### 1. 必须满足的条件和用于比较的偏好严格分开

必须满足的条件负责直接排除餐厅。例如：

- 必须是川菜；
- 三公里以内；
- 价格不超过二档；
- 晚上九点仍然营业；
- 必须支持预约；
- 排除某一家餐厅。

用于比较的偏好只负责给已经通过过滤的餐厅排序。例如：

- 更安静；
- 食物更好；
- 更适合约会；
- 更地道；
- 在其他条件接近时距离更近。

“想吃川菜”中的“川菜”是必须满足的餐饮类别；“想吃地道的川菜”中的“地道”是需要通过评论证据判断的长尾软偏好。两者不能混成一条。

### 2. 来源控制权固定

发生冲突时，程序固定执行以下顺序：

```text
本轮用户明确要求
>
之前对话仍然有效的要求
>
用户长期画像
>
场景默认倾向
>
系统临时默认值
```

这个顺序不是每轮交给大模型猜。大模型负责理解用户说了什么，程序负责保证来源控制权不会被模型幻觉改变。

### 3. 大模型理解语言，程序执行事实和规则

大模型负责：

- 结合本轮问题和历史对话理解要求变化；
- 识别场景；
- 判断哪些是硬条件、哪些是软偏好；
- 理解“最重要、其次、先……再……”等排序关系；
- 在需要时读取历史推荐商家事实；
- 为评论检索生成与当前问题有关的正面和反面说法；
- 把已经确定的前五和证据写成自然中文回答。

程序负责：

- 检查大模型输出是否符合固定结构；
- 检查餐饮类别是否来自固定类别表；
- 合并四个来源并处理冲突；
- 计算经纬度直线距离；
- 生成安全的参数化查询并执行硬过滤；
- 从评论库中召回真实评论；
- 计算证据分和最终排序；
- 限制最终回答只能使用真实商家事实和真实评论。

### 4. 没有证据就不能硬说

系统不允许大模型凭常识说某家店安静、地道、适合约会或某道菜好吃。最终出现的这些结论必须来自：

- 可直接核对的商家事实；或
- 当前评论库中实际取回的原始评论。

如果正面和反面评论同时存在，回答必须保留风险，不能只挑好话。

### 5. 大结果用于审计，小结果进入下一轮

一次真实推荐可能产生上万行完整运行结果，因为里面保存了：

- 大模型原始输出；
- 完整统一状态；
- 每条硬条件执行前后的数量；
- 每家餐厅每条偏好的正反评论候选；
- 每个分数的组成；
- 最终前五及完整回答。

这些内容保存在磁盘中用于复查，不会全部塞进下一轮对话。下一轮只保留自然语言回答、前五家紧凑快照和本轮实际使用的评论编号。

## 四、收到一条用户问题以后，当前系统具体怎样运行

正式入口只要求调用方提供四样东西：

```text
用户编号
会话编号
用户本轮原话
本轮请求时间
```

然后按下面的顺序执行。

### 第一步：准备这一轮真正需要的上下文

第一轮会读取：

- 用户本轮原话；
- 真实用户长期画像；
- 用户长期画像中的当前位置；
- 六个场景基准；
- 当前时间。

第二轮以后会读取：

- 上一轮结束时的完整统一状态；
- 本轮用户原话；
- 之前的用户与助手对话；
- 之前真正展示过的商家顺序、商家编号和距离；
- 从上一状态中恢复的长期画像偏好；
- 从上一状态中恢复的场景偏好。

长期画像和场景不需要每轮重新从外部读取，但它们没有消失，而是已经被保存在上一轮状态的偏好记忆中。

### 第二步：让大模型理解这一轮发生了什么变化

大模型不是只看这一轮孤立的句子，也不是只输出一张“新增清单”。它会基于上一轮完整状态、历史对话和本轮原话，重新生成当前对话层面的完整要求。

例如：

```text
第一轮：想找近一点的川菜。
第二轮：最好安静一些。
第三轮：第三家太远了，别推荐这么远的。
```

第三轮理解时，大模型能够按“第几轮、第几家”调用历史商家查询工具，读取第三家的真实距离。假设第三家距离是 3 公里，它可以把当前最大距离改成小于或等于 3 公里，并记录这个数值来自哪家历史商家。

大模型在这一阶段只填写理解语言必须填写的内容，例如：

- 场景；
- 搜索地点和大致范围；
- 硬条件的字段、比较方式和值；
- 软偏好的字段、方向、目标和先后顺序；
- 固定字段以外的长尾要求；
- 对应的用户原话和对话轮次。

用户不需要在问题里说“强度 75”。本轮明确软偏好由程序统一补成最高强度；画像和场景的强度来自已有数据。

### 第三步：程序生成唯一的完整统一状态

大模型的精简结果会被程序补齐成一份固定结构。后续地点计算、硬过滤、评论检索、排序和回答都只读取这份状态，不再各自重新理解用户原话。

程序会在这里完成：

- 给每条要求生成稳定编号；
- 补齐单位和对应商家字段；
- 验证每条要求确实来自用户说过的话；
- 验证菜系属于固定餐饮类别；
- 把本轮、历史、画像和场景按固定控制权融合；
- 合并相同偏好；
- 保存被覆盖但以后可能恢复的偏好；
- 让软偏好和长尾偏好共享同一个连续优先级顺序。

### 第四步：确定搜索中心并计算距离

如果用户说出城市、街区、商圈、地标或地址，大模型当前会给出近似中心经纬度和合理搜索半径。

例如：

```text
费城唐人街
→ 中心点约为 39.9526, -75.1564
→ 搜索半径约为 1.5 公里
```

程序会自动把这个半径补成“最大直线距离 1.5 公里”的硬条件，然后根据中心点和 2,447 家餐厅的经纬度计算真实球面直线距离。

当前地点坐标仍由大模型估算，没有接入真实地理编码服务。因此它能够工作，但不是最终的地点解析方案。

### 第五步：补齐营业时间要求

用户明确说“今晚九点”“周六中午”时，这个到店时间成为硬条件。

用户没说到店时间时，程序使用本轮请求发生的当地时间，补一条可以被后续用户要求覆盖的营业默认值。

营业时间来自 Yelp 历史数据，不是实时营业接口。2,447 家餐厅中目前有 2,304 家存在每周营业时间，143 家没有。执行营业硬过滤时，营业时间未知的商家会被排除。

### 第六步：执行结构化硬过滤

硬过滤工具不再理解自然语言。它只接受已经校验过的统一状态，并把条件生成安全的参数化查询。

当前能够执行的硬条件包括：

- 餐饮类别；
- 最大或最小距离；
- 价格档位；
- 指定或排除商家；
- 最低或最高评分；
- 最低或最高评论数量；
- 指定到店时间仍然营业；
- 是否支持预约、配送、外带、室外座位；
- 是否适合儿童、适合多人；
- 是否支持轮椅、允许带狗、可以停车。

大模型不会自己写查询语句。程序只从封闭字段表生成查询，用户内容作为参数传入，不会直接拼进查询语句。

每条硬条件都会记录：

- 执行前还有多少家；
- 执行后还有多少家；
- 排除了多少家；
- 其中多少家是因为该字段未知而被排除；
- 实际执行的查询条件。

### 第七步：为每条软偏好准备正反评论检索说法

当前有 14 种固定评论特征：

- 食物质量；
- 服务；
- 性价比；
- 安静程度；
- 拥挤程度；
- 排队时间；
- 分量；
- 停车便利程度；
- 宠物友好程度；
- 适合家庭；
- 适合约会；
- 适合聚会；
- 辣度；
- 清洁程度。

这 14 种特征都有固定的正反基础含义。在线推荐时不再把所有特征都交给模型重写。食物质量、分量和辣度这三类明显受具体菜品影响的要求，会在它们本轮真正生效时结合用户问题生成检索说法；其余固定特征直接读取已经写好的正反描述。这样既能让“牛排质量好”真正查牛排肉质、味道和熟度，又不会为了“安静”“停车方便”之类含义稳定的要求重复消耗模型输出。

例如用户要吃牛排，而且当前有“食物质量好”的偏好，检索说法会关注牛排的肉质、味道和熟度，而不是只找宽泛的“食物不错”。

固定表以外、但可以用评论判断的要求称为长尾软偏好。例如“地道的川菜”。长尾要求的正反说法与四路融合放在同一次大模型调用中生成，不会为每条要求或每条评论重复调用大模型。

### 第八步：只在硬过滤留下的商家中查真实评论

当前评论数据共包含 499,314 条餐饮评论。重新切分后得到 624,746 个评论片段，并使用本地文字向量模型生成 1,024 维向量，已经导入本地 Qdrant 评论库。

评论切分规则是：

- 优先保留完整句子；
- 每个片段最长约 900 个字符；
- 相邻片段重复上一片段末尾的一句话，避免上下文突然断开；
- 只有单个句子本身超过 900 字符时，才优先在词语边界继续切；
- 不丢弃长评论的尾部；
- 评论库用于定位片段，真正展示证据时仍能还原完整原评论。

检索严格限制在硬过滤后的商家编号中，不会从其他餐厅召回评论。评论库在线只返回片段编号、评论编号、商家编号、文字和相似程度，不再把每条 1,024 维向量一起传回。方向比较需要的向量会按片段编号从本地文件一次读取，并在本轮全局去重。

对每条偏好、每家餐厅：

1. 第一档正面和反面各粗召回 15 条；
2. 只有结果取满且明确证据不足 5 条时，才把该商家扩大到 30 条，仍不足再扩大到 60 条；
3. 粗召回相似度门槛暂定为 0.55；
4. 同一原评论的多个片段会合并；
5. 正文相同或只差标点空白的重复评论只算一次；
6. 每条评论同时计算它像正面说法的程度和像反面说法的程度。

只有满足以下规则才会成为证据：

```text
正面相似度至少 0.60
并且比反面相似度高至少 0.05
→ 正面证据

反面相似度至少 0.60
并且比正面相似度高至少 0.05
→ 反面证据

其他情况
→ 模糊，丢弃，不参与分数
```

当前已经不再把每条评论交给 DeepSeek 判断方向，因此大幅降低了早期方案一次请求数万词元的成本。

### 第九步：计算证据分并排出前五

每家餐厅、每条偏好分别最多保留 5 条正面证据和 5 条反面证据。

一条证据的影响由两个因素决定：

```text
它与当前要求有多相关
×
它离本轮请求时间有多近
```

时间权重当前使用 730 天的减半周期。评论越新影响越大，但旧评论不会突然变成零。

证据数量也会影响可靠程度：

```text
数量可靠度 = min(1, log(证据条数 + 1) / log(6))
```

一条偶然评论影响较弱，五条及以上达到完整数量可靠度。

一条偏好下的商家证据分为：

```text
证据分 = 0.5 + 0.5 × 正面证据分 - 0.5 × 反面证据分
```

没有相关证据时保持中性 0.5，不会被硬说成满足或不满足。

多条偏好的权重为：

```text
偏好权重 = 偏好强度 / 100 × 0.75 ^ (优先级 - 1)
```

这里既保留了用户说出的先后顺序，也不会出现“第一条满足、第二条完全不满足，却仍然只看第一条”的极端逐层排序问题。

最终排序为：

```text
最终分 = 0.6 × 多条偏好综合分
       + 0.3 × Yelp评分 / 5
       + 0.1 × 距离分
```

评分和距离只承担兜底与稳定排序作用，用户的当前偏好和评论证据占主要部分。硬过滤后的全部商家都会参与这一步，不会先按评分砍成前十。

### 第十步：生成给用户看的自然推荐回答

程序先固定最终前五顺序，然后每家最多选 4 条代表性完整评论：

- 优先覆盖高优先级偏好的正面证据；
- 至少保留一条重要反面或条件风险；
- 同一评论不会重复发送。

最后只调用一次大模型生成整份自然中文回答。回答不要求机械输出固定表格，但必须遵守：

- 不能改变前五顺序；
- 不能增加或删除商家；
- 不能编造评论、菜品或商家事实；
- 不能把“食物总体不错”改成“某道菜一定好吃”；
- 必须保留重要反面证据；
- 距离只能说经纬度直线距离，不能说步行距离；
- 营业时间只能说历史 Yelp 数据记录，不能声称实时准确。

### 第十一步：保存下一轮真正需要的内容

一轮完成后，当前实现会保存：

- 本轮完整统一状态；
- 用户原话；
- 最终自然语言回答；
- 真正展示的前五家商家紧凑快照；
- 每家商家实际用于回答的评论编号。

商家快照包括当时的顺序、商家编号、名称、经纬度、直线距离、价格档位、类别和已计算的偏好分。

因此下一轮用户说“第二家怎么样”“第三家太远了”时，不需要重新把完整运行文件送给大模型。系统可以先从紧凑快照定位商家，再按需读取商家事实或评论证据。

正式 Agent 入口现在会把会话事件、完整统一状态和历史商家快照写入 PostgreSQL。程序重启后可以按用户编号和会话编号恢复上一状态。完整评论审计等大结果不会写进每条会话事件，而是压缩成独立文件，数据库只保存结果编号、摘要和文件位置。内存存储仍保留给不访问数据库的快速测试。

## 五、统一状态里面到底保存什么

每轮只有一份完整状态，不再同时维护另一套容易冲突的“增加、删除、修改清单”。它主要包括以下部分。

### 1. 会话基本信息

- 用户编号；
- 会话编号；
- 当前是第几轮；
- 状态修订次数；
- 本轮用户原话。

### 2. 用户位置和本轮搜索中心

用户长期位置与本轮搜索中心分开保存。用户可以长期在一个位置，但本轮明确要求去另一个商圈吃饭。

搜索中心保存：

- 地点类型；
- 地点名称；
- 中心经纬度；
- 必要时保存对应商家编号。

### 3. 当前场景

当前内置六种场景：

- 随便吃；
- 约会；
- 商务；
- 朋友聚餐；
- 家庭聚餐；
- 一个人吃。

没有场景就保存为空，不会强制套用“随便吃”。每个场景只提供较弱的初始搜索范围和软偏好，用户可以在后续对话中修改。

### 4. 当前硬条件

只保存数据库或现有工具可以直接执行的结构化要求。每条硬条件都保存字段、比较方式、值、单位、来源原话、来源轮次以及必要的推导依据。

### 5. 场景或系统默认条件

默认条件与用户明确硬条件分开保存。用户一旦明确提出同字段要求，明确要求会替代默认值。

默认值不是不可修改的系统禁令，只是用户没有表达时帮助第一次推荐起步的条件。

### 6. 当前生效软偏好

每条软偏好保存：

- 比较什么；
- 希望更高、更低、更接近某个值、匹配还是避开；
- 目标值；
- 偏好强度；
- 当前总体优先级；
- 当前控制来源；
- 所有支持它的来源依据。

优先级回答“先看什么、再看什么”；偏好强度回答“同一来源内部这条倾向有多稳定”。本轮明确偏好固定为最高强度，用户不需要自己报数值。

### 7. 偏好记忆

四路融合不会把输掉的偏好静默删除。每条候选偏好都会记录为：

- 当前生效；
- 与当前生效偏好同义，作为支持依据；
- 被更高来源压住；
- 被硬条件压住。

例如用户长期喜欢日料，但本轮明确要吃川菜。日料画像不会参与本轮排序，但仍保留在偏好记忆中。下一轮用户取消川菜要求时，它仍有可能恢复。

### 8. 长尾要求

固定字段以外的要求单独保存文字、行为和优先级。例如“要地道的川菜”。当前可以通过评论判断的长尾偏好会进入评论证据检索。

如果长尾要求被用户表达为绝对必须满足，但当前没有能够严格核验它的结构化字段或工具，现有固定工作流还不能把它当作百分之百可靠的硬过滤。后续 Agent 应决定是调用新工具、要求用户澄清，还是降为有证据的排序要求，而不是让程序凭关键词硬猜。

### 9. 历史推荐商家快照

只保存真正展示过的商家，不保存未展示的上万行候选过程。这样既能支持多轮指代，又能控制上下文大小。

## 六、四个来源具体怎样融合

四个来源分别是：

1. 本轮问题；
2. 之前对话；
3. 长期画像；
4. 场景默认。

程序不是简单把四张表拼起来，而是按字段判断同义、冲突和遮蔽。

例如：

```text
本轮：想吃川菜，安静最重要
历史：距离近一些
画像：平时偏爱日料、看重食物质量
约会场景：安静、适合约会、服务好
```

处理结果是：

- 川菜成为硬条件；
- 画像中的日料被川菜硬条件压住，但继续留在偏好记忆；
- 本轮安静控制“安静程度”这个字段；
- 约会场景的安静与本轮同方向，只作为支持依据，不再生成重复偏好；
- 历史距离、画像食物质量和场景约会适合程度继续保留；
- 最终重新生成连续优先级。

偏好强度不会推翻来源控制权。即使画像强度很高，本轮用户只要明确说了相反要求，本轮仍然优先。

## 七、长期画像当前怎样接入

第一轮按真实用户编号读取长期画像，再转换成统一软偏好。

转换规则是：

- 一条原始画像信号对应一条偏好；
- 不把多个菜系或多个区域提前压成一个列表并共用同一强度；
- 长期画像只能产生软偏好，不能替用户制造硬条件；
- 每条画像偏好保留历史证据次数和最近确认时间；
- 画像内部根据原始得分、证据次数和最近确认时间排顺序。

画像可以提供菜系倾向、常去区域、价格档位以及 14 种评论特征倾向。与本轮类别硬条件冲突的画像菜系会被压住，不会污染当前候选范围。

当前系统已经保存画像的历史次数和最近确认时间，但画像时间衰减仍没有形成一套完整、经过测评校准的在线公式。这是后续可以继续改进的地方。

## 八、餐厅数据和类别数据当前是什么样

| 合计词元 | 6,877 | 6,824 |
| 评论证据排序 | 约 8.06 秒 | 约 1.67 秒 |
| 整轮耗时 | 约 17.63 秒 | 约 16.46 秒 |
| 用户看到第一段回答 | 等完整回答结束 | 约 7.43 秒 |

本地文字向量模型首次加载约 14.90 秒，这是应用启动成本，不包含在上表 16.46 秒的单轮耗时中。正式常驻服务只加载一次，不应每轮重新启动。

## 十、当前真实存在的问题

### 1. 长尾评论仍可能发生“对象错配”

当前向量检索能够理解“地道”这类长尾含义，但可能把“地道的南亚菜”误当成“地道的川菜”，因为两句话在“地道菜系”层面很相近。

因此下一步评论证据层要增加对象核对：评论不仅要像“地道”，还要真的在谈川菜、四川风味、麻辣、花椒或当前目标菜系。不能只凭相似度高就当证据。

### 2. 地点坐标不是由真实地图服务返回

当前能根据地点运行距离过滤，但坐标由大模型估算。后续需要接入真实地点查询工具进行校准。

### 3. 营业时间不是实时状态

当前只能使用 Yelp 历史每周营业时间。节假日、临时停业和当天变更无法保证。

### 4. 商家主营类别仍可能不够准确

只要商家原始类别中带有某个类别就可能被选入。以后需要区分主营类别和伴随类别，避免“带有牛排馆标签但主营不像传统牛排馆”的结果。

### 5. 14 种固定特征还没有完成全量离线打分

现在所有评论特征仍按当前问题在线检索。后续可以用人工标注、大模型生成训练数据和小模型微调，把高频 14 种特征离线聚合成商家长期分数，在线只处理长尾问题。

### 6. 没有明确时间时，“现在营业”过滤得过重

当前逻辑在用户没有表达时间时，会自动使用请求发生时的当地时间，并把营业状态作为严格硬条件。牛排测试因此从 62 家直接降到 4 家。建议改成：用户明确说“现在、马上”时才按当前时间硬过滤；用户说了具体日期和时间时按指定时间硬过滤；用户完全没说时间时不做营业硬过滤，只在结果中展示历史营业时间和不确定风险。该修改尚未实施。

### 7. 新版测评体系还没有完成

旧的单一命中式测评不能证明“推荐理由有证据、硬条件没有违反、四路偏好融合正确、回答对用户有用”。新版需要重新建立覆盖多轮修改、硬过滤、偏好顺序、证据真假和最终回答质量的测试集。

### 8. 长期画像进入本轮排序的内容过多

牛排测试中有 20 条画像偏好进入当前状态，其中“避开比利时菜、爱尔兰菜、巴基斯坦菜”等要求与本轮牛排候选几乎没有区分作用。它们虽然不会违反硬条件，却会稀释真正相关的食物质量、价格、距离等偏好。后续需要在保持“本轮 > 历史 > 画像 > 场景”控制顺序的基础上，再判断每条画像偏好与本轮任务是否有关；无关偏好应留在偏好记忆中，但不参与本轮算分。该修改尚未实施。

## 十一、当前已经有的工具能力

新版当前已经存在以下可复用能力：

1. **读取真实用户长期画像**：按用户编号读取画像并转成统一偏好。
2. **读取历史推荐商家**：按轮次和第几家读取当时保存的距离、价格和类别等快照。
3. **读取商家完整基础事实**：按商家编号查询，一次最多五家，返回地址、评分、类别、属性和营业时间。
4. **计算地理距离**：根据搜索中心和商家经纬度计算直线距离。
5. **结构化硬过滤**：根据统一硬条件生成参数化查询并过滤真实商家。
6. **评论证据排序**：在硬过滤商家范围内检索正反评论并排出前五。
7. **最终推荐总结**：把固定前五、商家事实和少量代表性证据写成自然回答。

正式入口现在已经由外层 Agent 判断用户是要重新推荐、直接回答，还是查询上轮商家事实。完整推荐内部仍按固定顺序调用这些能力，防止模型跳过硬过滤、扩大评论检索范围或改变已经算好的商家顺序。

## 十二、当前 Agent 运行框架怎样工作

Agent 框架位于相邻的 `src/yelp_agent/agent_platform/`。它不是只服务餐饮的临时代码；餐饮推荐只是第一项接入能力，以后可以继续注册旅游、酒店、景点或其他生活服务工具。

### 1. 主模型决定做什么，推荐工具保证内部顺序

主模型当前可以直接回答，也可以调用完整餐饮推荐工具或商家事实查询工具。例如用户只问“第二家有没有停车位”，系统从 PostgreSQL 恢复上轮商家快照，定位第二家后只查询商家事实，不会重新跑一遍推荐。

如果用户发起或修改推荐，主模型调用完整餐饮推荐工具。这个工具内部固定执行：

```text
四路需求融合并生成评论检索说法
    ↓
地点和距离计算
    ↓
结构化硬过滤
    ↓
候选商家范围内的评论证据检索和排序
    ↓
按固定顺序生成最终回答
```

外层主模型不能在推荐完成后再改写一遍结果，也不能擅自把第三、第四家重新说成更值得推荐。

### 2. 每个工具调用前后都经过统一检查

所有工具都会依次完成参数结构验证、执行前处理、是否允许调用检查、超时和重试包装、输出结构验证、执行后处理以及结果记录。业务工具只负责读取事实或完成推荐，不需要各自重复写日志、计时和异常处理。

### 3. PostgreSQL 保存可以恢复的会话事实

数据库使用只追加事件保存会话创建、轮次开始、用户消息、模型请求、工具调用、工具结果和轮次结束。完整餐饮状态单独按版本保存，避免旧状态覆盖新状态。应用异常退出时，未完成轮次可以标记为中断，之后仍可继续会话。

逐片返回的几百个小片段不会逐条写入数据库。数据库只保存最终完整回答。大体量推荐审计结果会压缩成独立文件，数据库只保存摘要、结果编号和文件位置，因此下一轮不会把上万行评论过程重新送给模型。

### 4. 统一统计整轮用量和耗时

运行框架会把主模型和推荐工具内部模型的调用次数、输入输出词元、工具次数和分阶段耗时合并到同一轮结果中。现在能够区分应用首次加载本地模型的启动时间、单轮总时间、评论检索时间、最终回答时间和第一段回答到达时间。

## 十三、下一步开发顺序

当前 Agent 骨架、PostgreSQL 持久化、真实模型、餐饮工具、整轮统计和逐片回答已经完成。接下来建议按实际问题的影响顺序继续：

1. 修正“用户没说时间就按现在营业硬过滤”的规则，并增加对应回归测试；
2. 给长期画像增加本轮相关性判断，无关偏好留在记忆中但不参与本轮算分；
3. 区分传统牛排馆、cheesesteak 等主营语义，减少仅凭附带 Yelp 类别进入候选的问题；
4. 修复长尾证据的目标菜系或目标菜品错配；
5. 接入真实地点查询服务；
6. 增加多个只读工具的安全并行执行；
7. 开始 14 种高频特征的数据标注、小模型微调和离线商家分数聚合；
8. 建立覆盖硬条件、多轮修改、偏好控制、证据真假、推荐顺序和回答质量的新测评体系。

长对话摘要、最近结果位置记忆和旧内容按需取回已在通用 Agent 框架中完成，
不再列为待办。最近原话、当前对象、前十项结果顺序、餐饮状态版本和旧话题摘要
会分别保存；主模型只有在确实追问更早内容时才调用历史搜索工具。

## 十五、后续接手者必须牢记的事实

1. 当前只做餐饮推荐，真实候选范围是 2,447 家 Yelp 餐厅。
2. 菜系是硬条件，不是软偏好；“地道”之类的程度要求才进入评论证据排序。
3. 硬过滤永远先于评论检索，评论检索永远限制在硬过滤商家范围内。
4. 大模型负责理解语言，但不能自己写最终查询、决定证据分或偷偷改变前五顺序。
5. 四路控制权固定为：本轮问题 > 历史会话 > 长期画像 > 场景默认。
6. 用户不需要说偏好强度；本轮明确要求由程序补成最高强度。
7. 当前评论方向由正反向量相似度和差值判断，不再逐条调用 DeepSeek。
8. 完整运行结果用于审计，不会整包进入下一轮；下一轮使用统一状态和前五紧凑快照。
9. Agent 调度层、PostgreSQL 会话持久化和统一整轮用量记录已经实现；完整审计结果仍放在独立压缩文件中，不会进入下一轮模型历史。
10. 当前最先要修的是默认营业时间导致候选过少，以及无关长期画像偏好进入本轮算分；不能重新把旧 Agent 或旧排序模型接回来当主流程。

## 十六、2026-08-27 评论召回更新

评论召回已经从单独按意思查找，升级为按意思和按关键词两路同时查找，再按各自名次合并。Qdrant 新集合保存624,746个评论片段的两套索引，并继续使用硬筛商家编号和请求时间限制查询范围。

单问题全量标签实验表明，每边2种不同的正反说法是当前速度和召回的合适起点；增加到4～5种没有继续提高总体召回，耗时反而从约6.85秒增加到12.84～19.12秒。正式需求融合提示词因此固定生成2种不同角度说法。公共数据结构仍允许最多5种，只用于后续评测，不代表在线每次都执行5种查询。

本轮只修改召回入口，没有修改P/N方向判断、时间数量聚合和最终商家评分。混合召回找回更多正确评论的同时也带来更多噪声，因此下一步应讨论候选截断与证据评分，而不是继续增加查找说法数量。

正式提示词中的两条说法不再是任意两句：第一条必须是评论可能给出的直接结论，第二条必须是可观察表现。用正式生成结果单跑一次，“地道川菜”的直接证据召回达到19.47%，较宽口径达到15.65%，耗时7.14秒。能由评论查证的 must_have 开放要求也已接入评论检索，并固定补成优先级1、强度100；需要距离或历史工具的 must_have 不进入评论库。
