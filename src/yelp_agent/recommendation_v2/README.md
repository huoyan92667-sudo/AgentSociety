# recommendation_v2 当前完成情况

这套新版推荐流程与旧推荐流程分开开发。所有新版逻辑和新版生成数据都放在本目录中，不修改旧推荐流程。

## 当前做到哪一步

当前已经打通的是：

```text
用户本轮问题
    +
上一轮结束时的完整要求
    +
之前的对话和历史推荐商家
    +
用户长期画像
    +
场景默认要求
    ↓
大模型理解本轮变化
    ↓
程序检查来源、事实和固定优先顺序
    ↓
生成本轮新的完整要求数据
```

正式在线流程已经继续接通到结构化硬过滤和基于正反评论证据的加权软偏好排序。最终自然语言推荐回答还没有开始生成。

## 已经完成的内容

### 1. 统一要求结构

每轮对话结束后只保存一份完整状态，不再额外维护“新增、删除、收紧、放宽”清单。

完整状态目前能够保存：

- 当前用户问题和对话轮次；
- 当前定位和搜索中心；
- 当前场景；
- 必须满足的硬条件；
- 第一次推荐时使用、但可以被用户修改的场景默认条件；
- 用于逐层排序的软偏好及其先后顺序；
- 被当前要求压住、但以后可能恢复的历史偏好；
- 暂时还不能直接执行的要求；
- 之前真正展示过的商家、位置、距离、价格和类别。

当前硬条件支持：

- 餐饮类别；
- 最大距离；
- 价格档位；
- 指定或排除商家；
- 评分和评论数量；
- 预约、配送、外带、室外座位；
- 适合儿童、适合多人；
- 轮椅支持、允许带狗、可以停车。

软偏好既可以使用上述结构化商家事实，也可以使用后续评论层提供的14种商家特征：

- 食物质量、服务、性价比；
- 安静程度、拥挤程度、排队时间；
- 分量、停车便利程度、宠物友好程度；
- 适合家庭、适合约会、适合聚会；
- 辣度、清洁程度。

14种评论特征已经完成“寻找可能相关评论”这一步。当前在线流程会把少量候选完整评论交给大模型判断正面、负面、条件性和未知，但还没有把全量历史评论离线聚合成长期商家分数。

### 2. 六个场景默认要求

已经建立六个场景：

- 随便吃；
- 约会；
- 商务；
- 朋友聚餐；
- 家庭聚餐；
- 一个人吃。

每个场景包含第一次搜索使用的默认距离，以及该场景内部排好先后的软偏好。没有识别出场景时，场景保持为空，不强行套用“随便吃”。用户后续提出新要求时，大模型可以修改这些默认值。

### 3. 多轮问题理解和四路融合

正式多轮入口每轮只调用一次大模型。大模型会同时看到：

- 上一轮结束时的完整状态；
- 用户这一轮的原话；
- 之前的对话轮次；
- 之前推荐过的商家及其真实顺序和距离；
- 第一轮读取的长期画像；
- 第一轮或场景变化时读取的场景默认要求。

大模型负责理解用户的意思并生成本轮完整状态。例如用户说“第三家太远了”，模型可以读取历史记录中第三家真实距离，再生成新的最大距离条件。

程序负责执行不会变化的规则：

```text
硬条件：本轮明确要求 > 之前对话

软偏好：本轮明确偏好 > 之前对话 > 长期画像 > 场景默认
```

偏好强度只用于同一来源内部排序，不能让长期画像反过来覆盖用户本轮明确要求。不同来源表达相同要求时会合并依据；发生冲突时，被覆盖的偏好不会删除，而是保存在偏好记忆中。

### 4. 长期画像接入

已经能够根据真实用户编号读取现有长期画像，并转换成统一软偏好。

转换时遵守：

- 一条原始画像信号对应一条软偏好；
- 不把多个菜系或多个区域提前压成一条；
- 每条偏好单独保留强度、历史证据次数和最近确认时间；
- 长期画像只能产生软偏好，不能制造硬条件；
- 长期画像内部按照强度、证据次数和最近确认时间排序。

### 5. 历史推荐商家读取

已经建立历史商家事实读取能力。大模型可以按照“第几轮、第几家”或者商家编号，读取历史推荐中保存的：

- 商家编号和名称；
- 经纬度和当时计算的距离；
- 价格档位；
- 原始类别；
- 已保存的商家特征分数。

工具只返回历史中真实保存的值，找不到时明确返回找不到，不编造数据。

### 6. 餐厅范围和真实类别统计

从旧商家全集3973家商家中，严格按照原始 `Restaurants` 类别选出了2447家餐厅，并统计出餐厅中真实出现的319种类别。

`business_catalog/` 负责完成这一步。它是离线数据生成程序，不参与每轮正式推荐，但目前不能删除，原因是：

- `data/dining_catalog/v1/businesses.parquet` 是它生成的2447家餐厅范围；
- `data/dining_catalog/v1/categories.parquet` 是它生成的319种原始类别统计；
- 固定类别表使用这份类别统计作为输入；
- 统一商家基础事实使用这份餐厅范围作为输入；
- 删除生成程序后，原始数据变化时无法重新构建上述数据。

因此它平时不会运行，但承担数据可重建和数据来源核对的职责。更准确的理解是“餐厅范围生成器”，不是正式推荐功能。

### 7. 固定餐饮类别表

319种真实类别已经全部进入固定类别表，每一种都有明确结论：

- 179种可以交给大模型选择；
- 140种不允许作为餐饮筛选类别，包括伴随出现的非餐饮类别和没有筛选意义的宽泛类别。

固定表没有维护“用户可能说法”。大模型只能从允许选择的真实类别中挑选，程序负责检查它是否乱填。

已经建立部分真实上下级关系，例如：

```text
Chinese
├── Cantonese
├── Dim Sum
├── Hot Pot
├── Szechuan
└── Taiwanese

Japanese
├── Izakaya
├── Ramen
└── Sushi Bars

Bars
├── Cocktail Bars
├── Sports Bars
└── Wine Bars
```

商家基础事实仍然保留 Yelp 原始类别。以后大模型选择上级类别时，程序先把搜索类别展开成真实下级类别，再直接检查商家的原始类别中是否命中。

### 8. 统一商家基础事实

已经为2447家餐厅生成一行一个商家的统一基础事实，包含：

- 商家编号、名称和地址；
- 经纬度；
- Yelp 原始类别；
- 原始评分和原始评论数量；
- 价格档位和对应美元人均近似区间；
- 预约、配送、外带、室外座位；
- 适合儿童、适合多人；
- 轮椅支持、允许带狗；
- 车库、路边停车、停车场、代客泊车、验证停车；
- 根据五种停车方式汇总出的“是否可以停车”。

评分和评论数量直接来自原始 Yelp 商家文件，没有根据现有评论重新计算。

四档价格的项目换算规则目前是：

| 价格档位 | 美元人均近似区间 |
|---:|---:|
| 1档 | 0～10美元 |
| 2档 | 11～30美元 |
| 3档 | 31～60美元 |
| 4档 | 61美元以上 |

商家属性没有明确值或者原始值为 `None` 时，一律保存为未知，不会当成否。以后评论证据层可以提供补充证据，但本层不会根据评论猜测商家事实。

### 9. 14种评论特征的两路粗筛

评论粗筛只负责从49.9万条餐厅评论里找到“可能谈到某个特征”的候选，不在这里判断正面、负面，也不直接计算商家分数。这批每项最多20条的旧候选现在只作为离线分析产物保留，正式软排序已经改为在当前前10家餐厅的全部评论向量中重新检索正反证据。

第一路使用旧词表。旧词表原来的正向词和负向词在这一层合并使用，例如 `quiet`、`noisy` 都只表示这条评论可能谈到了安静程度。程序保存实际命中的词，但不会因为命中某个词就直接下结论。

第二路使用意思相近查找。程序先把全部餐饮评论按段落和完整句子组成不超过900字符的片段，为每个片段保存文字向量，再用14种特征两端的完整描述查找相近内容。例如安静程度同时用“安静、适合交谈”和“吵闹、必须提高音量”两端去找，避免只找到正面一端。

评论片段只用于定位。两路候选合并后，真正保存给后续细判断的是完整原始评论，同一条评论不会因为命中多个特征而重复保存。每条“评论—特征”关系会明确记录：

- 是否由旧词表找到；
- 命中了哪些旧词；
- 是否由意思相近查找找到；
- 最接近哪一条特征描述；
- 意思相近程度的原始数值。

意思相近程度只用于粗筛候选内部取前几条，不表示评论一定相关，更不表示正面或负面。没有真正相关评论时，下一步细判断应当全部判为不相关，使该商家特征保持未知。

全部评论片段向量会保留下来。以后用户提出14种固定特征以外的问题时，可以直接用同一份向量查找评论，不需要重新处理49.9万条原始评论。

当前真实生成结果为：

- 旧词表从499,314条餐厅评论中找到227,364条不同评论、289,252条“评论—特征”关系；
- 全量向量包含617,797个评论片段，每个片段1024维；
- 意思相近路线按每家商户、每种特征最多20条，生成685,160条关系；
- 两路合并后得到310,561条不同完整评论、929,826条关系；
- 其中244,666条仅由旧词表找到，640,574条仅由意思相近路线找到，44,586条被两路同时找到。

真实抽查同时展示最高分候选和最弱尾部候选。最高分样例能够补到“停车绕了很久”“声音大到必须喊”“厕所很干净”等旧词表未命中的说法；最弱尾部也明确存在无关评论。当前没有凭感觉增加统一分数线，原因是不同特征的数值分布不同。下一步应先标注一批真假相关样本，再决定各特征的候选数量或分数边界。

## 已经接入正式流程的过滤能力

当前 `RecommendationWorkflow` 已经完成：

1. 用户没有另行指定搜索中心时，使用长期画像中的当前位置作为搜索中心；
2. 地点工具根据搜索中心和2,447家餐厅经纬度计算本轮真实距离；
3. 硬过滤工具把固定结构中的类别、距离、价格、评分、评论数、商家编号和真假属性转换成参数化查询；
4. 上级类别会通过固定类别表展开到真实下级类别；
5. 价格或真假属性缺失时严格按硬条件排除，并记录每条条件排除了多少未知值；
6. 每条条件都保存执行前后数量，最终返回满足全部硬条件的真实商家事实和距离。

真实接口测试已经完成一次：大模型从中文问题生成4条硬条件和2条软偏好，程序对2,447家真实餐厅执行过滤，最终留下9家。

## 已经接入正式流程的软排序能力

当前硬过滤完成后继续执行：

```text
按评分、评论数、距离生成完整基础顺序
    ↓
取基础顺序前10家作为本轮证据判断范围
    ↓
对每条评论型软偏好，在这10家的全部评论向量中分别取最多5条正面候选和5条反面候选
    ↓
DeepSeek逐条判断：支持 / 反对 / 条件性 / 无关
    ↓
程序根据正面、反面和条件性证据权重计算每项满足分
    ↓
程序结合偏好优先级和强度计算总分
    ↓
评分基础顺序只在总分相同时兜底
```

距离、评分、价格等已有准确商家事实的软偏好不会去评论里猜，也不会浪费大模型调用，而是直接比较真实字段。14种评论特征才进入评论检索和大模型判断。

大模型不能直接决定商家层级和最终顺序，也不能返回自己编写的评论引文。它必须对输入中每个真实评论编号逐条判断，程序检查编号不重不漏且属于对应餐厅后，再计算：

```text
单项满足分 = (正面证据权重 + 0.5 × 条件性证据权重 + 1)
             ÷ (正面 + 反面 + 条件性证据权重总和 + 2)
```

少于2条有效证据时保持未知；满足分不低于0.75且至少有2条正面证据才算明确满足；不高于0.25且至少有2条反面证据才算明确相反；其他情况均为条件性结论。Yelp商家的总评论数不会当作分母，因为没有谈到某项体验不能算反面证据。

每条偏好的影响大小为：

```text
偏好权重 = 偏好强度 ÷ 100 × 0.75 ^ (优先级 - 1)
```

所有单项满足分使用加权几何平均得到总分。这样第一项偏好仍然最重要，但不能一票否决其他偏好；一家店如果第二、第三项存在明显短板，会被共同拉低。最终仍分别返回：

- 支持用户要求的评论；
- 反对用户要求的评论；
- 只在特定时间、位置、菜品等条件下成立的评论。

真实牛排例子已经使用 `deepseek-v4-flash` 跑通：

- 用户问题为“这次想吃牛排”；
- 大模型把牛排正确转换成 `Steakhouses` 硬条件；
- 2,447家餐厅经过类别硬过滤后留下62家；
- 按评分直接生成基础顺序，已经不再调用旧画像排序模型；
- 长期画像留下菜品质量、性价比、拥挤程度和价格档位四条有效软偏好；
- 三条评论型偏好各调用一次DeepSeek，价格档位直接比较商家事实；
- 三次评论判断共使用64,925个输入词元和10,215个输出词元；
- 最终结果保存了每项满足分、偏好权重、总分、层级以及正面、负面和条件性完整评论；
- 新版前三名为Ken Love's BYOB、Dump-N-Roll、Broncos Brazilian Steakhouse。

与上一版相比，原第一名Delilah's没有进入评分前10；原先因为少量菜品好评而直接升到第一的问题已经消失。现在没有一家餐厅仅凭第一条偏好就获得“明确满足”，正反证据混合的餐厅被保守地判为条件性。当前仍有两个后续问题：一是Yelp附带的`Steakhouses`类别仍可能纳入主营并非传统牛排馆的商家；二是每家正反各5条完整评论使一次真实请求达到约6.5万输入词元，需要在不损失正反覆盖的前提下继续压缩成本。

当前 `RecommendationWorkflow` 已返回融合要求、地点计算、硬过滤候选、评分基础顺序、逐评论证据判断和最终软排序列表，但还没有生成面向用户的最终推荐文字。
