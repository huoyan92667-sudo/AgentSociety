# Full Retrieval V2 召回率瓶颈诊断与后续改进方向

## 1. 文档状态

- 记录日期：2026-08-08
- 当前状态：问题已确认，暂缓修改，等待后续专门的召回优化阶段
- 对应系统：Full Retrieval V2 + Item-KNN
- 当前候选上限：Top-500
- 当前召回路线：Quality、Category、TF-IDF Text、Location、Item-KNN
- 后续排序器：Hybrid V1、Hybrid V2-A Logistic

这份文档用于冻结第 16 步结束时发现的召回瓶颈。当前不修改召回代码，后续功能继续按项目计划开发；需要优化召回时，以本文档中的数据、口径和问题拆分作为起点。

## 2. 两种 Recall@500 口径

当前系统默认推荐用户尚未体验过的新商家，并要求目标商家在任务 `cutoff_time` 前至少存在一条历史评论。因此需要同时报告两个口径。

### 2.1 全任务 Recall@500

```text
最终 Top-500 中包含目标商家的任务数 / 全部任务数
```

这个口径会把以下任务也计为召回失败：

- 目标商家是用户已经体验过的商家，但当前策略主动排除了历史商家；
- 目标商家在 cutoff 前没有历史评论，不属于当时可召回目录。

### 2.2 政策内 Recall@500

```text
最终 Top-500 中包含目标商家的任务数
/
目标商家当时具备目录资格且不在用户历史中的任务数
```

这个口径更适合判断召回算法本身在当前“推荐新商家”政策下的表现。

## 3. Train、Validation 与 Legacy Test 召回结果

| 数据集 | 全部任务 | 历史商家目标 | 目录不合格目标 | 政策内任务 | 召回命中 | 全任务 Recall@500 | 政策内 Recall@500 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Rolling Train | 17,920 | 958 | 133 | 16,829 | 9,514 | 53.09% | 56.53% |
| Validation | 5,000 | 326 | 29 | 4,645 | 2,378 | 47.56% | 51.19% |
| Legacy Test | 5,000 | 372 | 31 | 4,597 | 2,249 | 44.98% | 48.92% |

对应的失败数量：

| 数据集 | 全任务未命中 | 政策内未命中 |
|---|---:|---:|
| Rolling Train | 8,406 | 7,315 |
| Validation | 2,622 | 2,267 |
| Legacy Test | 2,751 | 2,348 |

说明：

1. Train、Validation 和 Test 都存在接近一半目标未进入最终 Top-500 的问题，因此这不是只出现在某一个切分中的偶然现象。
2. Train 的政策内 Recall@500 比 Validation 高 5.34 个百分点。Train 的 cutoff 通常更早，任务时点平均目录约有 2,973 家商家；Validation 平均约有 3,280 家商家。同样选择 500 家时，较早的 Train 任务覆盖目录的比例更高。
3. Test 是项目已经观察过的历史测试集，只能称为 `Legacy Test`，不能称为全新盲测，也不能再用于训练、阈值调整或模型选择。

## 4. 为什么详细原因分析主要使用 Validation

构建候选时，系统可以额外保存每个任务中每条路线的完整 Top-500 来源记录。Validation 保存了：

```text
data/task_dataset/full_retrieval_v2_item_knn/
  validation_route_provenance.parquet
```

其中记录：

- `task_id`
- `route`
- `route_rank`
- `business_id`
- `route_score`

这份 Validation 来源文件共有约 1,246 万行，因此可以判断正确商家是“五路都没找到”，还是“某一路已经找到、但在最终融合中被淘汰”。

Train 有 17,920 个滚动任务。如果保存五路各 500 条来源，理论上最多接近 4,480 万行。为了控制磁盘和构建开销，当前 `configs/retrieval.yaml` 只为 Validation 保存来源明细。Legacy Test 也没有保存来源明细。

因此：

- Train、Validation、Legacy Test 都能计算最终 Recall@500；
- 目前只有 Validation 能准确拆分五路未覆盖和 RRF 融合挤出；
- 不能在缺少来源文件的情况下，假设 Train/Test 的失败构成与 Validation 完全相同。

如需验证 Train 的失败构成，优先对固定种子的 Train 子集保存来源明细，而不是立即生成完整的 4,000 多万行文件。

## 5. 当前五路候选如何压缩为 Top-500

五条路线各自最多返回 500 条记录，但不同路线可能返回同一家商家。因此它们不是 2,500 家互不重复的商家。

在 Validation 上：

- 五路来源记录最多约 2,500 条；
- 去重后平均约 1,629.5 家不同商家；
- 当前系统使用 RRF 将它们压缩为最终 500 家。

RRF 分数定义为：

\[
RRF(b)=\sum_r\frac{1}{60+rank_r(b)}
\]

其中 `rank_r(b)` 是商家 `b` 在路线 `r` 中的排名。系统不直接相加不同路线的原始分数，只使用路线排名；五条路线当前拥有相同权重。最后按照 RRF 分数降序排列，同分时按照 `business_id` 升序排列，并截取前 500。

## 6. Validation 失败原因拆分

Validation 政策内共有 4,645 个任务：

| 结果 | 任务数 | 占政策内任务 | 占政策内未命中 |
|---|---:|---:|---:|
| 进入最终 Top-500 | 2,378 | 51.19% | — |
| 至少一路找到，但被 RRF 挤出 | 1,479 | 31.84% | 65.24% |
| 五路 Top-500 都未找到 | 788 | 16.96% | 34.76% |

五路 Top-500 并集对正确商家的覆盖率是：

```text
(2378 + 1479) / 4645 = 83.04%
```

而经过 RRF 压缩后的 Recall@500 只有 51.19%。因此当前最大的可观测工程瓶颈不是五条路线完全缺少信号，而是约 1,630 家不同候选被固定 RRF 压缩为 500 家时产生了明显损失。

### 6.1 RRF 对单路候选不利

| 目标商家进入的路线数量 | 任务数 | 最终被保留 | 保留率 |
|---:|---:|---:|---:|
| 0 | 788 | 0 | 0.00% |
| 1 | 1,222 | 220 | 18.00% |
| 2 | 1,288 | 859 | 66.69% |
| 3 | 853 | 805 | 94.37% |
| 4 | 394 | 394 | 100.00% |
| 5 | 100 | 100 | 100.00% |

只被一条路线发现的目标商家有 82% 被最终融合淘汰。RRF 偏爱被多条路线共同发现的商家，即使这些商家在每条路线中的名次都不高。

例如：

```text
目标商家只在 Item-KNN 排第 300：
RRF = 1 / (60 + 300) ≈ 0.00278

另一个商家在三条路线都排第 400：
RRF = 3 / (60 + 400) ≈ 0.00652
```

第二家商店没有任何一路特别突出，但会因为多路累计分数超过目标商家。

### 6.2 五路都未找到的 788 个目标

这部分才属于路线自身覆盖能力不足。它们与最终召回成功的目标存在以下相关差异：

| 诊断特征 | 最终召回成功 | 五路均未找到 |
|---|---:|---:|
| cutoff 前历史评论数中位数 | 217.5 | 46.5 |
| 与用户历史细分类别重叠率 | 89.87% | 73.86% |
| 距用户历史活动中心中位数 | 1.43 km | 2.83 km |
| 距离超过 10 km 的比例 | 2.06% | 9.77% |
| 用户最终给出 1–2 星的比例 | 12.15% | 21.57% |

这些结果表明，五路均未覆盖的目标更可能是：

- 相对冷门、历史证据较少的商家；
- 用户较少体验过的细分类别；
- 偏离用户历史活动中心的商家；
- 用户偶然体验但最终并不满意的商家；
- 由临时场景或当前需求驱动、仅靠历史画像无法推断的商家。

上述结果是相关性诊断，不能直接当作因果结论。

Item-KNN 在三类任务中通常都能正常返回候选，五路均未覆盖并不是由 Item-KNN 文件缺失或大面积空结果造成，而是目标商家的协同信号不足以进入该路线的前 500。

## 7. 评测标签本身的限制

当前 ground truth 是“用户下一条评论对应的商家”，不等价于“系统应该推荐且用户会满意的商家”。

在 Validation 的 4,645 个政策内任务中：

- 约 15.65% 的目标最终被用户打了 1–2 星；
- 约 13.82% 的目标最终被用户打了 3 星；
- 约 70.53% 的目标最终被用户打了 4–5 星。

因此当前 Recall 更准确地衡量：

```text
系统能否预测用户下一家会评论的商家
```

而不是完全衡量：

```text
系统能否推荐一家用户最终会满意的商家
```

此外，Yelp 数据没有用户发起推荐时的自然语言 Query。用户可能因为聚会、约会、求婚、临时位置或预算变化选择一家与长期历史偏好不同的商家；当前纯历史召回无法观察这些条件。

## 8. 为什么 Hybrid V2-A 无法修复召回损失

当前执行顺序是：

```text
五路召回并集：平均约 1,630 家
→ 固定等权 RRF 截断为 500 家
→ Hybrid V1 / Hybrid V2-A 对这 500 家重新排序
```

Hybrid V2-A 只能重新排列已经保留下来的 500 家商店。被 RRF 提前淘汰的 1,479 个 Validation 目标，以及五路均未找到的 788 个目标，不会进入 Hybrid V2-A 的输入，因此任何后续重排模型都无法把它们恢复。

## 9. 后续改进方向

### 9.1 第一优先级：修复候选融合阶段

将流程调整为：

```text
五路去重并集，平均约 1,630 家
→ 学习型召回融合 / Pre-ranker
→ 选择最终 500 家
→ Hybrid V2 精排
```

可比较的候选融合方法：

1. 当前等权 RRF，作为冻结基线；
2. Validation 调优的加权 RRF；
3. 为各路线保留最低配额，保护只被单路发现的商家；
4. Logistic 或 LambdaMART 学习型 Pre-ranker；
5. 根据用户历史长度、画像可靠性和路线缺失情况动态选择路线权重。

学习型融合必须只使用 Rolling Train 标签训练，在 Validation 选择配置，模型冻结后才能读取 Legacy Test。

### 9.2 建立召回容量曲线

不能只报告 Recall@500。应在相同冻结任务上评估：

```text
Recall@50 / 100 / 500 / 800 / 1000 / 1500 / route-union
```

同时记录候选数量、延迟、Parquet 体积和后续特征计算成本，以确定召回率与工程成本的平衡点。

### 9.3 改进单条召回路线

- Category：加入细分类别、近期类别偏好和兴趣漂移，不只使用长期平均画像；
- Text：在严格时间边界下尝试语义 Embedding 召回，改善 TF-IDF 对同义表达的不足；
- Location：由单一历史中心升级为近期中心或多个活动中心；
- Item-KNN：尝试更稳定的图相似度、用户聚类、矩阵分解或 Two-Tower 协同召回；
- Review Aspect：将 cutoff 前的商家评论证据用于专门的 Aspect/场景召回，而不是只在最终排序中使用；
- Long-tail：为历史证据较少的新商家保留探索通道，避免所有路线都偏向热门商家。

### 9.4 区分新商家推荐和重复到访

当前策略主动排除用户历史商家，但 Yelp 的真实下一次行为中存在重复到访。后续应分别定义并报告：

- `discover`：推荐尚未体验过的新商家；
- `revisit`：允许推荐用户以前体验过且可能再次访问的商家；
- `mixed`：根据当前请求决定是否允许重复商家。

不能继续把被政策排除的历史商家目标与普通召回失败混为一个数字。

### 9.5 改进评测标签和 Query-aware 评测

- 保留“预测下一次交互”的全量指标，便于与当前结果连续比较；
- 增加 `target_stars >= 4` 的满意行为子集评测；
- 后续增加自然语言请求后，分别比较 History-only、Query-only 和 History + Query；
- 如果从未来目标评论合成 Query，必须过滤商家名称、唯一描述和未来信息，并单独标记潜在泄漏风险，不能直接把这类结果当成真实在线 Query 效果。

### 9.6 再进行非线性精排

LambdaMART 等更强的排序器只能优化它看得到的候选。因此更合理的顺序是：

1. 先修复约 1,630 选 500 的候选融合损失；
2. 再比较 Logistic 与 LambdaMART 的精排能力；
3. 分开报告 Retrieval Recall 与进入候选后的 Ranking HR/MRR。

## 10. 后续验收标准

召回优化阶段至少需要满足：

1. 数据切分、时间边界、历史排除政策保持明确且可复现；
2. Validation 的政策内 Recall@500 高于当前 51.19%；
3. 不只提高 Route Union Recall，还必须提高最终融合 Top-500 Recall；
4. Train、Validation、Legacy Test 使用统一指标口径；
5. Legacy Test 不参与模型训练、权重选择和阈值调整；
6. 分别报告新商家、重复到访、正向目标和长尾商家结果；
7. 报告 Recall 提升带来的延迟、候选规模和存储成本；
8. 后续排序模型不得通过强制插入 target 的方式伪造召回命中。
