# 第24.1步：Router 状态摘要（RouteFacts）

## 这一步解决什么问题

第22步的 `AgentSession` 保存了完整运行状态，第23步的工具又会产生结构化
`ToolObservation`。这些信息适合保存和审计，但不适合让 Router 每次自己遍历大量
字典。

第24.1步新增一个统一入口：

```python
facts = RouteFacts.from_state(state)
```

它把复杂状态整理成 Router 真正需要的简单事实。以后 Rule Router、DeepSeek
Constrained Router 和 Cost-aware Router 都读取同一个 `RouteFacts`，不会各自实现
一套状态解析逻辑。

## 摘要中保存什么

- 当前任务类型、信息缺口和冲突字段；
- 当前请求是否包含硬约束；
- 用户明确提到的商家 ID；
- 当前候选范围以及范围是否已经确定；
- 召回、过滤、排序、详情、画像和比较工具的最近状态；
- 已召回、已排序、已有详情、已有画像和已比较的商家 ID；
- 上一个工具是否成功、没有结果、不可用或失败，以及错误码；
- 剩余步骤、工具调用、语义模型调用、Review RAG 调用和 Token 预算；
- 已校准的排序置信度及不确定原因（如果第19步提供了这些信息）。

摘要不会复制五路召回的500条特征、Hybrid V2全部分数或商家完整画像，因此 Router
不会因为读取状态而获得一大包不需要的原始数据。

## 多轮状态为什么要区别处理

不同观察结果的有效期不同：

- 候选召回结果可以跨轮复用；
- 商家静态详情和截止时间不变的聚合画像可以跨轮复用；
- 硬约束过滤必须针对当前一轮请求重新执行；
- Hybrid排序必须针对当前一轮请求重新确认；
- 候选比较结果也只属于当前一轮请求。

例如用户第一轮说“找牛排馆”，第二轮说“太远了，换近一点”。第一轮已经读取的
商家名称和地址不必重新查询，但第一轮的过滤与排序不能冒充已经处理了第二轮新增的
距离要求。

## `no_result` 和失败的区别

- `no_result`：工具正常工作，只是没有找到结果。后续可以追问是否放宽条件或保守
  结束。
- `unavailable`、`retryable_error`、`permanent_error`：工具本身不可用或执行失败。
  摘要会保留错误码，供后续 Router 或 Fallback 使用。

旧测试产生的非标准 observation 不会导致 Router 崩溃；状态摘要会忽略无法通过
`ToolObservation` 校验的记录。

## 本步测试

`tests/test_rule_route_facts.py` 覆盖：

1. 新请求的任务、缺口、硬约束和预算；
2. 召回、过滤、排序、详情的完整工具链；
3. 当前轮与历史轮观察的有效期；
4. 分批读取的详情和画像累积，以及当前轮比较结果；
5. 空结果、工具错误和旧格式记录；
6. 冲突字段、排序置信度和不确定原因。

## 本步明确没有实现

本步没有选择任何动作，也没有调用 DeepSeek。下一小步24.2才会根据这些事实计算
当前合法动作集合；后续 Rule Router 和 LLM Router 都会在这份共同事实之上做决策。
